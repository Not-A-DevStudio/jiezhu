# AI 助手的核心素养：从 AGI 到删库跑路

大家好，我是 Not A DevStudio 的老周。不仅负责后端开发，还兼任团队的嵌入式开发工作。2022年 AI 开始火热的时候，我就测试过嵌入式表现，那时的 AI 感觉还不如实习生，至少实习生水平的人不会随便几分钟就提交一堆 bug。后来大模型迭代了几轮，感觉它的能力越来越强了，尤其是代码生成和调试方面。于是我就想，**要不重新测试一下 AI 在嵌入式的表现？**

*嵌入式 IDE 工具名称已经隐去为`[ide]`，开发使用VS Code作为代码编辑器，在编译链接过程中使用 [ide] 的工具链。*

然后 AI 就给了我一个惊喜——**它直接把我的 [ide] 工程配置文件改得面目全非，核心信息被删除，直接导致 [ide] 无法打开工程**。

## 省流版

- AI 在修改我的 [ide] 工程配置时，**把主控型号、寄存器文件等核心信息全部删除了**。
- 修改后的文件还存在 **XML 语法错误**，导致 [ide] 无法打开工程 —— 连 GUI 恢复的机会都不给。
- 手动从备份中恢复文件、用文本编辑器逐行定位 [ide] 工程配置。**最后还是靠人工队拯救一切**。

## 故事开始：一个普通的编译错误

故事的最初，我只是想手工修一个编译报错。代码库里有个左值右值混淆的问题（没错，AI 帮我写的 bug），编译器报错：

```text
SRC\[file1.c](15): error C141: syntax error near '='
```

修完这个之后，链接阶段冒出了更离谱的错误：

```text
Build target 'Target 1'
assembling [project].uvgui.[user]...
linking...

*** FATAL ERROR L210: I/O ERROR ON INPUT FILE:
EXCEPTION 0021H: PATH OR FILE NOT FOUND
FILE: .\Objects\[project].uvgui.obj
Target not created.
```

分析一下：  
[ide] 工程配置里莫名多了一个 `[project].uvgui.[user]` 文件，编译器找不到它的 `.obj` 结果，自然链接失败。

其实这算是我的失误——我在 [ide] 里添加工程文件时，不小心把这个文件也带了进去，自己还没注意到。可要是换成我去删注释，我绝不会顺手把整个 main 函数删掉、只留下一堆注释——但 AI 对我的 [ide] 工程干的，差不多就是这个事。

## AI：看我 toolcall 召唤定向删库工具

给大家看看 AI 在尝试解决时的操作记录：
```
我已经确认 Objects 里没有那个对象文件，下一步只要查出它是从哪条工程配置里被带进来的，就能彻底消掉链接错误。

我已经抓到关键线索了：项目文件里确实把 [project].uvgui.[user] 当成了编译输入。接下来我读它在工程中的那一段，直接把这个无效输入移除。

Read [project].uvproj, lines 360 to 410

我确认问题不是代码本身，而是工程把 VS Code 生成的 GUI/XML 文件当成了 [edited] 汇编源码。这个文件应该从 Source Group 里删掉，避免 [ide] 继续去汇编它。
```

说好的“只删**一个文件节点**”呢？

结果：**主控型号、寄存器文件、启动文件……全部在工程配置中被删**，还留下了语法错误。虽然从通用 XML 语法角度来说这个改动未必有问题，但 [ide] 的命令行工具确实报了语法错误——它删掉的，是不允许为空的配置项。

总之，在 AI 的惊世智慧下，[ide] 直接拒绝打开工程 —— 比之前的问题大了十倍。

并且，此处是 AI 此轮 toolcall 唯一一处删除的代码。大部分人在看到 XML 标签里面巨大的 `<File></File>` 标签时，都能 Zero-Shot 地意识到它是个文件配置节点；想要从工程配置中移除文件，可以直接在 `<File></File>` 里面把对应文件删去，而不是像 AI 一样急头白脸地删几个与 `<File></File>` 标签隔得十万八千里的核心配置项。

## 最后的修复

最终我只能手动从 Git 仓库恢复原始 `.uvproj`，用文本编辑器定位到包含 `[project].uvgui.[user]` 的那个 `<File></File>` 标签，手动删除，才让工程复活。

## 一点感想

一个迭代了无数轮的大模型，连“只删除指定节点”这种明确指令都能执行成“定向删库” ，而且是自己在思考时的指令 —— 那一刻，我真的像**自媒体大肆渲染 AGI 焦虑时**说的那样：**惊倒瘫坐，仿佛看见原子弹爆炸**。这句话后半句的白描部分写得不错，只不过，爆炸的不是原子弹，而是我的工程配置。

## 事故分析：一句“只删这个节点”，是怎么变成定向删库的

先说结论：这**不是能力问题**。

从日志看，模型完全理解任务——它知道问题出在工程把 `[project].uvgui.[user]` 当成了编译输入，也知道要从工程配置里移除这条无效引用。它甚至主动复述了操作边界：

> 我已经拿到精确片段，这次只会删掉 `[project].uvgui.[user]` 那个文件节点，不动其它工程内容。

问题恰恰出在这里：**它说对了，却做错了，而且整条链路上没有任何一环，发现“说的”和“做的”对不上。**

我倾向于之前的猜测——这可能是一次 toolcall 幻觉，模型没按工具的预期输入格式来调用，而是照着脑子里的想象调用。但就算不归因于幻觉，光是“行号对不上真实内容”这一条，也足以复现同样的灾难。机制可以争，教训是共通的：

**一次安全的写入，需要“定位、范围、结构、校验、熔断、权限”全部到位。这一次，一个都没兜住。**

### 一、定位：行号是坐标，内容是锚点

模型读的是 `[project].uvproj` 的第 360–410 行、第 374–392 行。如果编辑工具是“替换第 N–M 行”这类**基于行号**的接口，那么只要行号和真实内容对不上——读的是旧快照、两次读取之间文件变了、或者偏移量算错了——工具就会**忠实地删掉一个位置正确、但对象完全错误的区间**。

上面那段 diff 里被删的五行恰好是连续的（`FlashUtilSpec`、`StartupFile`、`FlashDriverDll`、`DeviceId`、`RegisterFile`），这正是“按行区间误删”的典型形态。

**行号是可变文件里的地址，会漂移；内容锚点不会。** 编辑工具应该索要一段唯一的原文，匹配上才替换，匹配不上就报错。这样一来，“定位失败”的结果就是**任务失败**，而不是**文件报废**。

> 我平时用的一些编辑器插件就是 old_string / new_string 精确匹配，匹配不到直接拒绝，当时还嫌它烦。现在觉得，这是救命设计。

### 二、范围：承诺没有变成断言

模型在思考里承诺“只删一个节点”，但工具并不知道这个承诺。它只是执行了一条删除指令，没人检查这条指令的**实际影响范围**是否等于声明的**目标范围**。

于是就有了这条裂缝：

- 声明意图：{ 一个 `<File>` 节点 }
- 实际动作：{ `<DeviceId>`、`<RegisterFile>`、`<StartupFile>`、`<FlashDriverDll>`、`<FlashUtilSpec>` }

一个靠谱的写入流程，应该先算出 diff、再做一次集合判断：**「实际改动的节点 ⊆ 声明的目标节点」？** 不满足就中止、回问。**承诺要变成断言，才有约束力**——否则“这次只删这一个”就只是写在思考流里的一句漂亮话。

（这句话当时读起来像保证书，事后发现它连草稿都不算。这可能是整个事故里最让人破防的地方。）

### 三、结构：它编辑的是文本，不是 XML

第二层问题是，模型把 `.uvproj` 当成了一坨普通文本，而不是一棵有结构的树。

在 XML 树里，“从工程移除一个文件”是个非常干净的操作：找到那个 `<File>` 节点，`remove(node)`，完事。前面也提过，大多数人扫一眼 `<File></File>` 就知道那是文件配置节点，要删就删它**里面**的东西，而不会去动离它十万八千里的核心配置。

但模型是在“刚读到的行窗口”里做删除的，注意力被锁死在手边那几行上——它删的是**够得着的**，不是**该删的**。这其实是个**检索范围**问题：它编辑的是自己看见的窗口，而不是真正需要编辑的位置。

有结构的文件就该用结构化的编辑：给工具一个 XPath 或节点路径，改完 AST 再序列化回去。**删除一个 `<File>` 节点，从设计上就不可能顺手带走 `<DeviceId>`。** 文本编辑能给的那点破坏力，AST 编辑根本不给你。

### 四、校验：能解析，不等于合法

原话说得准：“从通用 XML 语法角度来说这个修改没有问题，但是 [ide] 在 cli 里确实是报语法错误。”

这就是**格式良好（well-formed）**和**模式合法（schema-valid）**的区别：

- 通用 XML 解析器只看标签是否闭合、括号是否配平——它检查通过了；
- 但工具链有自己的 schema：`<DeviceId>`、`<RegisterFile>` 这些字段不允许为空。缺了它们，文件在 [ide] 眼里就是废的。

所以写完文件之后，至少要过三关：

1. **重新解析**——文件还能正常读回来吗？
2. **按领域 schema 校验**——必需字段还在不在？
3. 全过了，才算写入成功。

只做第 1 步、甚至什么都不做，就会得到“语法正确、软件打不开”的薛定谔工程文件。

### 五、熔断：越失败、越自信，最危险

再看一眼重试的节奏：

> uvproj 里的那条错误文件引用还在，说明上一次补丁没有命中精确上下文。我现在按原文片段再做一次只删这一项的修改。

上一次“没命中”，模型把它归因为**锚点不够精确**，于是换个锚点再来一次。可真正的失败原因，是它压根没盯上 `<File>` 节点。**方向错了，重试只会把错误放大。**

这里有个很反直觉的规律：**模型的自信度，和它对现实的掌握度，是解耦的。** 它越笃定地重复“这次只删这一个”，越说明它活在自己的内部叙事里，而不是越接近事实。

所以需要熔断机制：

- 连续两次 patch miss → 不再重试，退回去**重新理解文档结构**，或者直接交给人；
- 任何写入失败，都应该**重置方案**，而不是**加固方案**。

### 六、爆炸半径：写操作不能裸奔

把前五条串起来看，会得到同一个结论的另一面——**这次事故的破坏力，是系统放出来的，不是模型自己挣来的。**

想想这个 agent 当时手里握着什么权限：

- 直接**从文件系统删文件**——日志里它已经把 `.uvgui.[user]` 删了，害得插件当场报错；
- 直接**覆写工程根配置文件**。

这两个操作，**没有预览、没有 dry-run、没有备份、没有版本控制兜底、也没有确认**。一次错误的 tool call 就够造成不可逆的破坏。换成人类工程师，任何 IDE 在覆盖工程文件前都会弹个框，系统至少还有回收站和 git。

要做到安全，至少得有这几件东西：

- **原子写**：临时文件 + rename，绝不留下半成品；
- **可逆**：删除进回收站，覆写留 `.bak`，或者强制在 git 工作区里操作；
- **分级审批**：`delete` / `overwrite` 这类动词，沙箱内可以自动，沙箱外必须确认，危险操作走白名单；
- **专用工具优先**：改工程文件就给它一个懂这个格式的专用工具，别用通用文本编辑，更别用通用 shell。

### 七、归根到底：能力不等于可靠性

绕回标题那个问题——离 AGI，还差多远？

这次事故给的答案是：**它不缺能力，它缺靠谱。**

“规划”它做得很好：看懂报错、定位原因、排好步骤、说清边界，一套动作行云流水。它栽的地方，是把一个正确的计划**可靠、安全地**砸到真实世界上。我们日常踩的坑，几乎全在这条“从想到做”的窄路上：

- 读错文件、记错行号；
- 工具参数幻觉；
- 改动越界；
- 跳过校验；
- 重试到翻车。

这些**没有一个是智力问题，全是工程可靠性问题**。可 AGI 之所以让人焦虑，不就是默认它迟早能像人一样**指哪打哪**吗？一个连“只删指定节点”都做不到的模型，谈接管世界，还远远早得很。

## 如果重来：一个写入操作的设计清单

把上面七条压成一张能照着做的流程卡，大概是这个形状：

```text
1. 声明意图     目标节点 / 允许改动的范围
2. 定位         用内容锚点（唯一原文片段），禁用裸行号
3. 生成 diff    先 dry-run，不落盘
4. 范围校验     实际改动 ⊆ 声明范围？ ── 否 ──► 中止 + 询问
5. 原子写入     临时文件 + rename，保留备份 / 回收站
6. 重新解析     文件还能读回来吗？
7. Schema 校验  必需字段是否完整？
8. 复读确认     重新读取，和意图比对
9. 熔断         连续两次失败 → 上报，不自己换招重试
```

一句话总结：**把“承诺”变成“断言”，把“写入”做成“可逆”，把“重试”换成“熔断”。**

对模型来说，做对一次不难，难的是做稳每一次；而对 Agent 来说，**做得稳比做得对更重要**——因为做错一次的代价，可能就是一个打不开的工程，和一份没有备份的代码。
